# ADR-002 — Persist scraping export generation state and results in Postgres, replacing synchronous per-request builds and the ephemeral job registry

- **Status**: Proposed
- **Date**: 2026-08-20
- **Deciders**: Leonardo Ferreyra
- **Tags**: scraping, exports, api, storage

## Context

Every Banner/Planner scraping export (Docentes, Secciones, Alumnos Matriculados,
Alumnos-Secciones) is rebuilt from scratch, synchronously, on every single download
request — `ScrapingExportsService` calls into `ScrapingExportsRepository` to re-query the
raw datasource and re-build the ExcelJS workbook on each `GET`, even when nothing has
changed since the last scrape completed. Grades RC improved on this with an async job
(`JobRegistry<GradesRcExportJobState>`, `src/modules/survey/shared/core/job-registry.ts`,
reused from the survey module's bulk-job pattern): `POST grades-rc/start` fires generation
in the background and the client polls `GET grades-rc/status/:jobId`. But `JobRegistry` is
an in-process `Map`, keyed by a generated `jobId`, with a 30-minute TTL — a result that was
already computed is lost on app restart or TTL eviction, and there is no way to ask "is
there already a current result for this export + period" without having the `jobId` from
the specific request that started it. The underlying cost — rebuilding unchanged data — is
only postponed by the TTL window, not solved, and the "already computed" signal does not
survive a user navigating away and returning later.

Separately, `openspec/specs/scrape-retention-and-cached-exports/proposal.md` commits to
deleting a scrape run's raw rows once the next run for the same period completes (latest-only
retention). Once that lands, an export can no longer be regenerated on demand from raw data
after the fact — whatever was computed at scrape-completion time is what has to be servable
later, which makes some form of persistence a hard requirement, not just a performance
nicety.

The proposal's own dependencies section assumed AWS S3 as the storage target, citing
`docs/CONTEXT.md`'s integrations table ("AWS S3 — Evidence and export file storage"). Reading
the actual code during design (not just the docs) shows that line is aspirational: a
repo-wide grep for `@aws-sdk/client-s3` shows it only in `package.json`/lockfiles and in
`docs/CONTEXT.md` itself — zero usage in any `.ts` file under `src/`. There is no S3
client wrapper, no upload/download service, and no bucket-key convention to follow anywhere
in this codebase, in `evidence/` or `ifc/` or otherwise, despite AWS credentials
(`AWS_ACCESS_KEY_ID`, `AWS_BUCKET_NAME`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`) already being
declared in `env.config.ts`. So the storage-location question could not be resolved by
"follow existing convention" — there isn't one yet.

## Decision

We will persist scraping export generation state and results in a new table on the **main**
datasource — one row per `(exportType, periodo, lang)` — carrying a `status`
(`running`/`completed`/`failed`; no `pending` — "no row yet" is its own distinct
`notGenerated` response shape rather than a status value, as decided during implementation),
timestamps, and the generated file as a `bytea` column. This table replaces both the
per-request synchronous build for the four sync exports
and the ephemeral `JobRegistry` for Grades RC. Generation is triggered automatically when the
relevant scrape run(s) reach `'completed'`, and can also be triggered manually per
`(exportType, periodo, lang)`; a download request serves the stored bytes directly when a
completed result exists, and reports current status (rather than blocking) when it does not.

The generated bytes are stored as `bytea` in Postgres, not in S3. This is a deliberate
correction of the proposal's original assumption, made after finding no existing S3
integration to build on.

## Consequences

### Positive

- Downloads are O(1) after the first generation per `(exportType, periodo, lang)` instead of
  rebuilding the workbook on every click — the entire point of the change.
- Generation state survives an app restart, unlike `JobRegistry`'s in-memory map, which
  directly fixes the "TTL evicts an already-computed result" failure mode.
- A user can leave and return and see accurate current status (`pending` / `running` /
  `completed` / `failed`) instead of a job-id-shaped black box that only the tab that started
  it could poll.
- Because the raw scrape data this is built from is about to become retention-limited to the
  latest run per period (the paired proposal), persisting the _result_ is what makes a past
  export still servable after its source raw rows are deleted — this is not just a caching
  optimization, it is now load-bearing for correctness.
- No new infrastructure dependency: reuses the same Postgres the rest of the application
  already runs on, with a plain `bytea` column and a migration, rather than introducing the
  first S3 client/service in the codebase as a side effect of an unrelated feature.

### Negative

- **Public API contract change.** The four sync export endpoints
  (`/scraping/exports/docentes|secciones|alumnos-matriculados|alumnos-secciones`) stop
  always streaming a file on `GET` — a first-time or not-yet-generated request now returns a
  not-ready/poll state instead. Grades RC's endpoints move from an ephemeral `jobId` key to a
  persisted `(exportType, periodo, lang)` key. Both require a frontend change; this is not a
  transparent backend-only improvement, and `openapi.json` must be regenerated in the same PR
  per `docs/POLICIES.md`.
- **`bytea` in Postgres grows the main database with binary blobs** it did not previously
  carry, and every regeneration is a full-row overwrite (old bytes discarded, no version
  history) — acceptable at today's export sizes (Grades RC already fully buffers its result
  in memory before this change even existed, so this adds no new peak-memory risk), but this
  does not scale gracefully if a future export type is large or if multiple language variants
  multiply row count materially. Migrating to S3 later is a live possibility, not foreclosed
  by this decision (add an `s3_key` column, backfill, drop `bytea` — non-breaking to callers
  since the contract is "download serves the current result" regardless of where it is
  physically stored) — but it is a real migration this ADR defers rather than avoids.
- **`docs/CONTEXT.md`'s integrations table is left stale** (still claims S3 is used for
  export storage) unless corrected separately — this ADR does not fix that line, since this
  change did not create the inaccuracy, it only discovered it.
- The new table's soft references to `scrape_run.id` / `planner_scrape_run.id` cannot be real
  foreign keys — those tables live on the separate `raw` / `planner-raw` datasource
  connections, and Postgres cannot enforce a FK across two different database connections.
  This is a deliberate, documented exception to `docs/POLICIES.md`'s "every FK uses
  `@JoinColumn`" rule, not an oversight.

### Neutral

- Grades RC's concurrency guard (one export at a time via an in-process flag) is preserved in
  spirit — the new table's `status = 'running'` on a given key now does the same job the
  in-process flag did, just persisted instead of process-local.
- The single-replica deployment constraint documented in `docs/CONTEXT.md` (Planner session
  state, grades-RC single-flight, survey `JobRegistry`) is neither resolved nor worsened by
  this change — persisting scraping-export state does not by itself make any of those three
  reasons go away.

## Alternatives considered

- **Keep `JobRegistry`, just raise the TTL / add a job-lookup-by-key index.** Rejected —
  it is still in-process memory, so it does not survive a restart, which is a hard
  requirement once raw data retention makes regeneration-on-demand unavailable after the
  fact. A longer TTL narrows the window without closing it.
- **Store generated files in S3 with metadata in Postgres**, matching what
  `docs/CONTEXT.md` claims is already the convention. Rejected for this change because no
  such convention actually exists in the code to build on — adopting S3 here would mean
  designing the first S3 integration in the codebase (client wrapper, key convention, error
  handling, bucket lifecycle) as a side effect of a scraping-exports feature, which is a
  separable concern better done deliberately. Left open as a future migration.
- **Keep exports fully synchronous, just add a short-lived read-through cache** (e.g.
  recompute at most once per N minutes). Rejected — it does not address the actual
  requirement from the proposal: explicit, visible generation state the user can watch across
  a session (pending/running/success/failed) and manually retrigger, which a bare cache
  cannot express.
