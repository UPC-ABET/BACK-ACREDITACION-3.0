# ADR-003 — Persist scraping exports as one language-neutral dataset per (exportType, period), rendered into a specific language only at download time

- **Status**: Proposed
- **Date**: 2026-08-22

## Context

[ADR-002](./ADR-002-persisted-pollable-scraping-export-generation.md) persists one row per
`(exportType, period, lang)` in `core.scraping_export_runs`, storing the fully-rendered `.xlsx`
as a `bytea` `file_bytes` column, unique on `(export_type, period, lang)`. That decision assumed
`lang` was a real dimension of the generated result, on a par with `exportType` and `period`.

It is not. Reading `src/modules/admin/scraping-exports/model/scraping-exports.labels.ts` and
`ScrapingExportsService`/`GradesRcExportRepository` shows `lang` never touches the underlying
query or merge — it only selects which static header/label strings, and which pre-written
`{es, en}` sentence, get written into the output file. `GradeRcExportRow.observations` already
carries language-neutral codes (`GRADE_RC_OBSERVATIONS.*`); the translation happens only at the
point the workbook is written. So generating a second language reruns the entire underlying
query for identical data — for the four sync exports (staff, sections, enrolledStudents,
studentSections) this is a wasted extra raw-datasource round trip.

For `gradesRc` it is worse than wasteful. It is a multi-minute Banner+Planner merge that pins a
pooled connection on the `exports-raw` datasource, guarded by a system-wide single-flight lock
(`gradesRcMergeStartedAt` / `isGradesRcMergeInFlight()` in `ScrapingExportGenerationService`)
because only one such merge can safely run at a time. That guard is not scoped to a period, and
`triggerForBannerRun`/`triggerForPlannerRun` fire one generation attempt per supported language in
a tight loop. Only the first language to claim the guard actually runs; the rest are silently
skipped (`this.logger.debug('...already in flight')`) and never auto-retried. In practice,
non-default languages of `gradesRc` routinely never get generated by the scrape-completion trigger
at all — someone has to notice the gap and manually `regenerate` each missing language, one at a
time, each re-consuming the full merge duration and re-holding the system-wide guard.

This surfaced directly: a user's `gradesRc` generation went stale
(`error.scrapingExport.staleGenerationDetected`, from `ScrapingExportGenerationService
.reconcileIfStale`), and even after their own row flipped to `failed`, retrying via `regenerate`
kept returning 409 `error.scrapingExport.alreadyGenerating` — the system-wide guard was still held
by a _different_ language's generation for the same or a different period. See
`openspec/changes/defer-export-language-to-download/proposal.md` for the full problem statement
and acceptance criteria this ADR exists to satisfy.

## Decision

We will make `core.scraping_export_runs` key generation state on `(exportType, period)` only,
persist a language-neutral dataset instead of a rendered file, and defer rendering into a specific
language to download time.

Concretely:

1. **Drop `lang` from the row's identity.** New unique constraint
   `UQ_scraping_export_runs_export_type_period` on `(export_type, period)`, replacing
   `UQ_scraping_export_runs_export_type_period_lang`. `triggerForBannerRun`/`triggerForPlannerRun`
   fire generation once per period, not once per `SUPPORTED_EXPORT_LANGS` entry.
2. **`core.scraping_export_runs` stops storing a rendered file.** Drop `file_bytes` and
   `file_name`. Both are fully derivable from static label data
   (`resolveLabels(<labels>, lang).fileName`) at download time — neither needs to be persisted.
3. **The four sync exports** (staff, sections, enrolledStudents, studentSections) — already fetched
   fully into memory today, no streaming involved — get a new nullable `rows_data jsonb` column on
   `scraping_export_runs`, written and read through the entity's normal `@JsonColumn()` decorator
   (its transformer already round-trips camelCase ↔ snake_case through ordinary
   `repository.save()`/`find()`, so no manual case handling is needed as long as this column is
   never touched through raw SQL). Rendering — applying `resolveLabels` for the requested language
   and building the workbook — moves to `download`.
4. **`gradesRc` gets a new child table, `core.scraping_export_gradesrc_rows`**, one row per graded
   line, with a real FK to `scraping_export_runs.id` (`ON DELETE CASCADE`) — both live on the main
   datasource, so unlike `sourceBannerRunId`/`sourcePlannerRunId` this one is not a soft reference.
   Columns mirror `GradeRcExportRow`, plus a precomputed `has_observations boolean` so the existing
   two-pass "clean sheet / observations sheet" read becomes an indexed `WHERE` instead of a jsonb
   array-length check. It is not safe to hold `gradesRc`'s rows in one `jsonb` blob the way the sync
   exports do — `prepareGradesRc`'s own comment records that a full period OOM-crashed the process
   when it was held whole, which is why it streams through a `TEMP` table today.

   Generation still merges into the existing session-scoped `TEMP` table on the `exports-raw`
   connection (unchanged), but now pages through it **once** (not twice, one pass tagging
   `has_observations` per row) and batch-inserts into the new child table on the main datasource,
   then releases the `exports-raw` connection immediately — instead of pinning it for the full
   merge-plus-render duration as it does today. Rendering into a requested language's `.xlsx`
   happens at download time, paging the child table twice (`has_observations = false`, then
   `true`), reusing the existing sheet-writing logic parameterized only by `lang`.

5. **Retention mirrors the already-accepted Banner/Planner "latest completed run only" rule**
   (`docs/CONTEXT.md` Business Rules): a generation's old `gradesRc` child rows are deleted only
   once a _new_ generation for the same `(exportType='gradesRc', period)` completes successfully —
   never before, preserving the existing "serve stale/prior result while a regenerate is running"
   philosophy from `openspec/specs/scrape-retention-and-cached-exports`.
6. **The migration clears `core.scraping_export_runs` outright** before reshaping the schema.
   Existing `(exportType, period, lang)` rows cannot be losslessly collapsed into the new
   per-period, language-neutral shape — there is no way to recover row-level data from an
   already-rendered `.xlsx` short of re-parsing it, and these are pure derived/cache rows with no
   audit or historical value. The next scrape completion or manual regenerate repopulates them
   under the new shape.
7. **The public wire contract is unchanged in shape.** `GET :exportType/status`,
   `GET :exportType/download`, `POST :exportType/regenerate` keep accepting an optional `lang`
   query param. Its meaning shifts from "which cached row to fetch" to "which language to render
   the language-neutral data into" at download time, and it becomes a no-op on `status`/
   `regenerate` (kept for backward compatibility, not removed). `openapi.json` is still regenerated
   in the same PR, since descriptions change even though types do not.

## Consequences

### Positive

- The Banner+Planner merge — the expensive, connection-pinning part of `gradesRc` — runs exactly
  once per period regardless of how many languages exist, closing the gap where non-default
  languages silently never auto-generated.
- The `gradesRc` single-flight guard is held for one merge's duration per period, not multiplied by
  language count — a scrape completion's auto-trigger can no longer starve itself.
- A failed/stale generation for one `(exportType, period)` is never blocked on retry by a
  _different_ language's leftover state, because there is no longer a per-language dimension to
  leak across.
- `gradesRc` pins the `exports-raw` pooled connection for materially less time: only for the merge
  and the single row-persist pass, not for the full merge-plus-render duration it holds today.
- Downloading a language that was never explicitly generated before no longer requires a fresh
  merge — it renders from whatever is already persisted, satisfying the proposal's AC-2 directly.

### Negative

- **Every download now re-renders the workbook**, rather than serving pre-baked bytes. This
  reintroduces, deliberately, exactly the kind of per-request work ADR-002 tried to eliminate for
  the four sync exports — the trade-off is accepted because rendering from already-fetched,
  language-neutral data (an in-memory array or an indexed table read) is materially cheaper than
  ADR-002's original problem (re-querying the raw datasource, or for `gradesRc`, rerunning the
  cross-source merge), so this is not a full reversion of ADR-002's benefit, but it is a real,
  named cost this decision accepts.
- **`core.scraping_export_gradesrc_rows` is a new table holding a full period's grade lines**,
  where the main datasource previously held nothing bigger than one binary blob per key. This grows
  the main database with structured data, and it is not obviously smaller than the `bytea` it
  replaces — a real dataset is not guaranteed to compress better than the `.xlsx` it renders into.
  Accepted because the prior blob already had to hold the same information (just rendered), and
  because this is a continuation of ADR-002's own already-accepted "grows the main DB" trade-off,
  not a new category of cost.
- **The migration destroys every existing cached export.** After it deploys, every `(exportType,
period)` shows `notGenerated` until the next scrape completion or a manual `regenerate` — a real,
  visible gap for whoever next opens the exports screen, not merely a schema formality. This is
  flagged as a runbook step, not something the migration can avoid.
- **`lang`'s meaning silently changes** on `status`/`regenerate` without a wire-level signal that it
  did. A client that previously relied on `status`'s `lang`-scoped response meaning "this specific
  language is ready" will now see a single per-period status regardless of which `lang` it asked
  for — behaviorally different even though the JSON shape does not change, and therefore not
  something contract testing against the schema alone would catch.

### Neutral

- The `gradesRc` cross-period single-flight guard itself is untouched — one merge at a time
  system-wide remains, for the same pooled-connection reason ADR-002 and `docs/CONTEXT.md`'s memory
  cap already accept. This ADR removes the guard's language-driven multiplication, not its
  existence.
- `es`/`en` remain the only supported languages; nothing here changes which languages exist or how
  many.
- Storage location stays Postgres on the main datasource — this ADR does not revisit ADR-002's
  rejection of S3, only what shape the persisted data takes within Postgres.

## Alternatives considered

- **Keep one `bytea` file per `(exportType, period, lang)`, but render every supported language
  eagerly at generation time instead of on request.** Rejected — this still runs the underlying
  merge/query once (fixing the duplication), but does not fix the actual complaint: `gradesRc`
  still pays the full render cost (and connection-pinning time) for every language on every
  generation, whether or not that language is ever downloaded, and the single-flight guard is still
  held for the sum of all languages' render time rather than the merge alone.
- **Persist `gradesRc`'s merged rows on the `exports-raw` connection instead of the main
  datasource**, next to the `TEMP` table it replaces. Rejected — `scraping-exports.module.ts`
  documents that connection as read-only and self-contained, sharing a physical database with
  Banner's and Planner's own raw scrape data, whose retention lifecycle (`docs/CONTEXT.md`'s
  "latest run only" rule) is unrelated to and could conflict with this feature's own retention
  needs. Writing application-owned, indefinitely-retained rows into a connection explicitly scoped
  to mirroring external raw data is the wrong boundary.
- **Store `gradesRc`'s rows as a single `jsonb` blob**, matching the sync exports' `rows_data`
  column. Rejected — `prepareGradesRc`'s own comment records that holding a full period in memory
  at once already OOM-crashed the process, which is exactly what the current `TEMP`-table-plus-
  paged-read design exists to avoid. A single `jsonb` column necessarily loads its full value on
  read, reintroducing that risk. A dedicated child table with keyset pagination preserves the
  existing streaming property.
- **Leave `gradesRc`'s system-wide single-flight guard scoped across periods as the actual fix**,
  i.e. make it per-period instead of per-language. Rejected as insufficient on its own: it would
  stop one period's `gradesRc` from blocking another's, but would not stop the _same_ period's
  languages from serially repeating the merge, which is the larger share of the waste and the
  direct cause of the `staleGenerationDetected` / `alreadyGenerating` conflict this ADR exists to
  close.
