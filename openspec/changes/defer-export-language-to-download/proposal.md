# Defer scraping-export language rendering to download time

**Slug**: `defer-export-language-to-download`
**Branch**: `feat/defer-export-language-to-download`
**Repos affected**: backend (frontend only if design finds the wire contract must change — see Risks)
**Created**: 2026-08-22

## Problem

`ScrapingExportGenerationService` ties `lang` into a scraping export's generation identity: one
persisted row, and one full run of the underlying query, per `(exportType, period, lang)`. But
`lang` never affects the underlying data — it only selects which static header/label strings and
pre-written `{es, en}` sentences get written into the output file (`scraping-exports.labels.ts`;
`GradeRcExportRow.observations` already carries language-neutral codes, translated only at write
time). So generating a second language reruns the entire query for identical data.

For the four sync exports (staff, sections, enrolledStudents, studentSections) this is a wasted
extra raw-datasource query per additional language — cheap, but pointless.

For `gradesRc` it is worse. It is a multi-minute Banner+Planner merge that pins a pooled connection,
guarded by a system-wide single-flight lock (`gradesRcMergeStartedAt` /
`isGradesRcMergeInFlight()`) because only one such merge can safely run at a time. That guard is
_not_ scoped to a period — and the auto-trigger path (`triggerForBannerRun` / `triggerForPlannerRun`)
fires one generation attempt per supported language in a tight loop. Only the first language to grab
the guard actually runs automatically; the rest are silently skipped (logged as "already in flight",
never surfaced or auto-retried). In practice, non-default languages of `gradesRc` routinely never get
generated by the scrape-completion trigger at all — someone has to notice the gap and manually
`regenerate` each missing language, one at a time, each re-consuming the full merge duration and
re-holding the system-wide guard, delaying everyone else's regenerate.

This is what a user hit directly: their `gradesRc` generation went stale
(`error.scrapingExport.staleGenerationDetected`, from `reconcileIfStale`) and, even after their own
row flipped to `failed`, retrying via `regenerate` kept returning 409
`error.scrapingExport.alreadyGenerating` — because the system-wide guard was still held by a
_different_ language/period's generation. The UI shows "failed", the retry says "busy"; nothing the
user can do closes that gap, and it costs them a working export until whatever unrelated generation
holding the guard finishes or times out.

## What already exists

- `ScrapingExportGenerationService`
  (`src/modules/admin/scraping-exports/api/scraping-export-generation.service.ts`) orchestrates
  generation for all five export types, persisting one row per `(exportType, period, lang)` in
  `core.scraping_export_runs` (`ScrapingExportRunEntity`, unique on
  `UQ_scraping_export_runs_export_type_period_lang`). `fileBytes` / `fileName` store the fully
  rendered `.xlsx` for that exact key — there is no language-neutral intermediate today.
- `ScrapingExportsService` (`.../api/scraping-exports.service.ts`) does the actual generation:
  `generateStaff` / `generateSections` / `generateEnrolledStudents` / `generateStudentSections` each
  re-query `ScrapingExportsRepository` and pick `resolveLabels(<labels>, lang)`; `generateGradesRc`
  / `prepareGradesRc` stream the Banner+Planner merge (`GradesRcExportRepository.openGradesRcExport`,
  a `TEMP` table behind one pinned pooled connection — see its OOM-avoidance comment) straight into
  an ExcelJS `WorkbookWriter`, applying `gradesRcExportLabels` / `gradesRcDescriptiveLabels` for
  headers/sheet names/observation text as it streams.
- All label/header/filename content is static TypeScript data (`scraping-exports.labels.ts`), not
  database content.
- `ScrapingExportsController` (`.../api/scraping-exports.controller.ts`) exposes
  `GET :exportType/status`, `GET :exportType/download`, `POST :exportType/regenerate`, all already
  accepting an optional `lang` query param (default `es`, `DEFAULT_TEMPLATE_LANGUAGE`).
- The `gradesRc` single-flight guard and the lazy staleness reconciliation (`reconcileIfStale`,
  `GENERATION_STALE_TIMEOUT_MS = 20 * 60_000`) were introduced by
  `openspec/specs/scrape-retention-and-cached-exports` (see its `design.md` / `tasks.md`) and
  `docs/adr/ADR-002-persisted-pollable-scraping-export-generation.md`, which explicitly decided to
  persist the fully-rendered bytes per `(exportType, period, lang)` rather than any intermediate —
  this change revises that specific part of ADR-002's decision.

## Goals

- The underlying query/merge for a given `(exportType, period)` runs at most once per generation
  cycle, regardless of how many languages `SUPPORTED_EXPORT_LANGS` lists — for `gradesRc` primarily
  (it is the expensive, blocking one), and for the four sync export types too, for consistency.
- Language selection (headers, filename, `gradesRc` observation sentences) is applied when a file is
  rendered for download, not baked in at generation time.
- The `gradesRc` system-wide single-flight guard is held only for the duration of one merge per
  period, not multiplied by the number of supported languages — so a scrape completion's auto-trigger
  can produce every supported language without any of them being silently skipped.
- A `regenerate` / `download` request for one language of an export never blocks, or is blocked by,
  a request for a different language of the _same_ `(exportType, period)` purely because of language.
- `staleGenerationDetected` and `alreadyGenerating` stay meaningful and uncoupled from language: once
  a `(exportType, period)` generation fails or goes stale, retrying it is not blocked by leftover
  state belonging to a different language of that same export/period.

## Non-goals

- Changing the cross-period `gradesRc` single-flight guard itself — one merge at a time system-wide
  remains, protecting the pooled connection under the memory cap noted in `docs/CONTEXT.md`; only the
  per-language multiplication of that guard's holding time is removed.
- Adding new languages or changing which languages are supported (`es` / `en` stay as-is).
- Migrating stored files from Postgres `bytea` to S3 — an explicitly deferred alternative in ADR-002,
  unrelated to this change.
- Any change to the underlying business logic/data of the four sync exports or `gradesRc` (grade
  resolution, observation rules, column contents) — only _when_ and _how_ language is applied changes.
- Frontend work beyond whatever is strictly required to keep the existing `status` / `download` /
  `regenerate` wire contract working (see Risks); if design finds no contract change is needed, no
  frontend PR is required at all.

## Acceptance criteria

1. **AC-1** — Given a Banner+Planner scrape pair completes for period P, when `gradesRc`
   auto-generation is triggered, then the underlying Banner+Planner merge runs exactly once for
   period P, not once per supported language.
2. **AC-2** — Given a completed generation exists for `gradesRc`/period P, when a client requests
   `download` for period P in a supported language that was never explicitly generated before (e.g.
   `en`, when only `es` had ever triggered generation), then the file is served without re-running
   the Banner+Planner merge.
3. **AC-3** — Given a `gradesRc` generation for period P has failed or gone stale
   (`staleGenerationDetected`), when a client calls `regenerate` for period P, then the call is not
   rejected with `alreadyGenerating` because of a _different_ language's leftover in-flight state for
   the same period — it is rejected only while period P's own generation, or a genuinely different
   period's, is running.
4. **AC-4** — Given the four sync export types (staff, sections, enrolledStudents,
   studentSections), when generation is triggered for period P, then the underlying raw-datasource
   query runs at most once per `(exportType, period)` per generation cycle, and each supported
   language is rendered from that one result.
5. **AC-5** — Given the existing `GET :exportType/status`, `GET :exportType/download`,
   `POST :exportType/regenerate` endpoints, when this change ships, then each endpoint's
   request/response shape is either unchanged, or the change is reflected in a regenerated
   `openapi.json` in the same PR, per `docs/POLICIES.md`.
6. **AC-6** — Given `core.scraping_export_runs` currently holds rows keyed by
   `(exportType, period, lang)`, when the migration for this change runs against an existing
   database, then it does not leave orphaned or duplicate rows per `(exportType, period)` and does
   not error on data created under the old key shape.

### Traceability

| AC  | Criterion                                                                             | Satisfied by                                                                                                                     |
| --- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | gradesRc merge runs once per period regardless of language count                      | `ScrapingExportGenerationService.triggerForBannerRun`/`triggerForPlannerRun` (loop removed)                                      |
| 2   | Downloading an ungenerated language serves from the existing artifact, no re-merge    | `ScrapingExportGenerationService.download` + `ScrapingExportsService.renderGradesRc`/`render*Excel`                              |
| 3   | Retry after failure/staleness isn't blocked by another language's in-flight state     | `ScrapingExportGenerationService.claimForGeneration`/`isGradesRcMergeInFlight` (lang dropped from key)                           |

| 5   | status/download/regenerate contract unchanged, or openapi.json updated in the same PR | `ScrapingExportsController`, `ScrapingExportStatusResponse`, `openapi.json`                                                      |
| 6   | Migration reconciles existing per-lang rows without orphaning/duplicating data        | `reshape-scraping-export-runs-language-neutral` migration                                                                        |

## Dependencies

- `openspec/specs/scrape-retention-and-cached-exports` (`proposal.md` / `design.md` / `tasks.md`) —
  the baseline this change revises: the per-`(exportType, period, lang)` caching model,
  `ScrapingExportRunEntity`'s current unique key, and the `gradesRc` single-flight guard.
- `docs/adr/ADR-002-persisted-pollable-scraping-export-generation.md` — records the decision to
  persist fully-rendered bytes per `(exportType, period, lang)`; this change revises that specific
  point, so it likely needs either an amendment note or a new ADR (the ADR gate in
  `/abet-design-feature` should decide which) recording the move to a language-neutral persisted
  artifact.
- A new forward-only migration on `core.scraping_export_runs` (schema change to the unique key and/or
  the stored-artifact shape) — per `docs/POLICIES.md`: CLI-generated timestamp, explicit
  `up()` / `down()`.
- Possibly `UPC-ABET/FRONT-ACREDITACION-3.0`, if design concludes the wire contract must change (see
  Risks).

## Open questions

None. Remaining unknowns are engineering questions (exact persisted-artifact shape, whether the
`status`/`download` wire shape needs to change) — captured above under Risks/Dependencies for
`/abet-design-feature` to resolve, not product decisions blocking this proposal.
